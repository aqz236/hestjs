# 依赖注入设计笔记

这份笔记记录 HestJS 注入容器的设计取舍。

## 为什么基于 TSyringe

要求只有一个：构造函数参数的类型元数据必须能在运行时拿到。
`reflect-metadata` + `design:paramtypes` 是唯一不需要额外编译插件的路径，
TSyringe 直接建在这套元数据之上，省掉一层自研容器的解析逻辑。

代价是编译必须开 `emitDecoratorMetadata`，所以测试与构建都不能用 esbuild。

## 注册与解析

容器把「注册」和「解析」分开：

- `register(token, provider)` 只登记，不实例化
- `resolve(token)` 才创建实例，并按 `Scope` 决定是否缓存

三种生命周期：

| Scope | 行为 |
| --- | --- |
| `Singleton` | 每个容器一份，首次解析后复用 |
| `Transient` | 每次解析都新建 |
| `Module` | 每个模块作用域一份，跨模块隔离 |

## 构造函数注入的边界

只有被 `@Injectable()` 标记的类才会被扫描参数类型。原因是
`design:paramtypes` 对未标记的类同样会产出元数据，但那些元数据往往来自
类型声明而非真实依赖（比如 `Function`、`Object`），直接照单全收会把容器
变成一个会吞掉拼写错误的黑洞。

因此 `Container.resolve` 对未注册的 token 采取白名单语义：命中已注册的
token 才注入，否则抛出可读的异常，而不是安静地返回 `undefined`。

## 常见陷阱

1. **接口不能作为 token**：接口在运行时不存在，必须用字符串或
   `InjectionToken` 显式标记。
2. **循环依赖**：构造期互相注入会得到未完成的实例。用属性注入或
   把共享部分下沉到第三个服务来打断环。
3. **默认参数**：带默认值的参数在元数据里仍然是必填的，容器不会跳过它。
   需要可选的依赖请显式标注 `@Optional()`。
